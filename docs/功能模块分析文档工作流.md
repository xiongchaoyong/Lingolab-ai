# 功能模块分析文档工作流

> 适用场景：对 PRD 中的某个功能模块进行完整的子功能拆解、用例图绘制、详细规格编写。
> 使用对象：产品经理、开发人员、技术文档编写者
> 最后更新：2026-05-29

---

## 一、工作流概述

本工作流将「功能模块分析文档」的编写拆分为 **三个阶段**，每个阶段产出独立、可审核的交付物。

```
阶段 1              阶段 2              阶段 3
子功能拆解 ────────► 用例图 ──────────► 子功能详细说明
(无序列表)         (drawio + png)      (需求/输入/处理/输出 + 流程图)
```

### 输出目录结构

每个功能模块单独一个文件夹，流程图和用例图分开存放，drawio 源文件和 png 图片也分开存放：

```
docs/功能模块需求分析/
├── 模块1-用户注册与多维度画像/
│   ├── 子功能清单.md                   # 阶段 1
│   ├── 详细规格说明.md                 # 阶段 3
│   ├── 流程图/
│   │   ├── drawio/
│   │   │   ├── flow-1.1-用户注册.drawio
│   │   │   ├── flow-1.2-登录与鉴权.drawio
│   │   │   └── ...
│   │   └── png/
│   │       ├── flow-1.1-用户注册.drawio.png
│   │       ├── flow-1.2-登录与鉴权.drawio.png
│   │       └── ...
│   └── 用例图/
│       ├── drawio/
│       │   └── 模块1-用例图.drawio
│       └── png/
│           └── 模块1-用例图.drawio.png
├── 模块2-英语水平智能测评/
│   └── ...
└── ...
```

### 三个阶段产出物

| 阶段 | 产出物 | 存放位置 | 格式 |
|:---:|------|------|------|
| 1 | 子功能清单 | `子功能清单.md` | 无序列表，编号 (1) (2) ... |
| 2 | 用例图 | `用例图/drawio/` + `用例图/png/` | draw.io 源文件 + PNG |
| 3 | 子功能详细说明 | `详细规格说明.md` | 文字/列表格式 |
| 3 | 流程图 | `流程图/drawio/` + `流程图/png/` | draw.io 源文件 + PNG |

## 二、阶段 1：子功能拆解

### 2.1 目的

将 PRD 中的功能模块拆解为可开发的子功能粒度，生成简洁的无序列表，让团队对模块范围有统一认识。

### 2.2 输入

- `docs/lingolab-ai-v1.0-prd.md` — 产品需求文档

### 2.3 操作步骤

在 Claude Code 中输入以下指令：

```
参考 docs/lingolab-ai-v1.0-prd.md 中的模块 X（模块名称），
将这个模块拆解为子功能，生成一个无序列表，
每一项用一句话简要描述该子功能。
列表项编号使用 (1) (2) (3) ... 格式。
输出文件保存到 docs/功能模块需求分析/模块X-名称/子功能清单.md。
```

### 2.4 产出格式

```markdown
# 模块 X：{模块名称} — 子功能清单

> 优先级：P0/P1/P2 | 参考 PRD：模块 X

- (1) {子功能名称} — {一句话描述}
- (2) {子功能名称} — {一句话描述}
- (3) {子功能名称} — {一句话描述}
```

每个子功能的判断标准：**一个子功能 = 一个独立可开发、可测试、可交付的最小单元**。一般一个模块拆 3-8 个子功能。

### 2.5 审核要点

- [ ] 每个子功能是否独立可开发、可测试？
- [ ] 是否有遗漏的边界功能？
- [ ] 描述是否一句话说清，不含糊？

---

## 三、阶段 2：用例图

### 3.1 目的

用 UML 用例图描述子功能与用户角色之间的交互关系，直观展示系统功能边界。

### 3.2 输入

- 阶段 1 产出的子功能清单
- PRD 中的用户角色定义

### 3.3 操作步骤

在 Claude Code 中输入以下指令（使用 drawio 技能）：

```
/drawio-skill 画一个 UML 用例图，描述模块 X（{模块名称}）的子功能用例。

用户角色：
- 学习者（普通用户）
- 教师（如涉及）
- 运营人员（如涉及）
- 系统

子功能列表：
- (1) {名称}: {描述}
- (2) {名称}: {描述}
- ...

要求：
- 每个子功能作为一个用例（椭圆）
- 角色用火柴人表示
- 用例间的 <<include>> / <<extend>> 依赖关系用虚线箭头标注
- 用例图边框标注模块名称
- 文件保存到 docs/功能模块需求分析/模块X-名称/用例图/drawio/模块X-用例图.drawio
```

### 3.4 输出文件

| 文件 | 路径 |
|------|------|
| drawio 源文件 | `用例图/drawio/模块X-用例图.drawio` |
| PNG 图片 | `用例图/png/模块X-用例图.drawio.png` |

## 四、阶段 3：子功能详细说明

### 4.1 目的

对每个子功能编写精炼的需求规格，聚焦核心逻辑和关键约束，作为开发编码依据。避免冗长模板化描述，只写开发真正需要的信息。

### 4.2 输入

- 阶段 1 产出的子功能清单
- 阶段 2 产出的用例图
- PRD 中对应模块的详细需求

### 4.3 文档结构

每个模块的 `详细规格说明.md` 按以下结构组织：

```
1. 功能简介        — 模块概述（3-5行）
2. 功能系统用例    — 引用用例图 + 功能点简述
3. 子功能详细说明  — 每个子功能按「介绍/输入/处理/输出」四段编写
```

**完整模板：**

```markdown
# 模块 X：{模块名称} — 详细规格说明

> 优先级：P0 | 参考：子功能清单.md、用例图

---

## 1. 功能简介

{3-5句话概述本模块的核心功能、目标用户、业务价值。}

---

## 2. 功能系统用例

> 用例图：`模块X-用例图.drawio`

本模块包含以下功能点：
- {功能点1}：{一句话描述}
- {功能点2}：{一句话描述}
- ...

---

## 3. 子功能详细说明

### 3.1 {子功能名称}

#### 1 介绍

{2-4句话描述功能需求，包括正常路径和关键异常响应。简明、完整、可验证。}

#### 2 输入

- **{字段名}**：来源={前端表单/API参数}，类型={string/int/...}，必填={✅/—}，有效范围={描述}
- **{字段名}**：来源={...}，类型={...}，必填={...}，有效范围={...}

#### 3 处理

1. {步骤1 — 校验或转换操作}
2. {步骤2}
3. {步骤3 — 含异常分支处理}

{校验规则和异常分支写在步骤内，不单独罗列。}

#### 4 输出

- **{字段名}**：去向={前端展示/数据库/API响应}，类型={类型}，说明={说明}
- 成功时：{用户可见结果}
- 失败时：{错误提示}

> 流程图：`flow-X.Y-名称.drawio`

---

### 3.2 {下一个子功能名称}
...
```

**编写原则：**

| 章节 | 要求 |
|------|------|
| **1 介绍** | 2-4句话，说清正常流程 + 关键异常响应。需求应简明、可验证 |
| **2 输入** | 列出核心输入字段（来源/类型/必填/有效范围），≤5个字段 |
| **3 处理** | 3-5步描述操作序列，校验规则和异常分支写在步骤内，不单独开章节 |
| **4 输出** | 输出去向 + 成功/失败时的用户可见结果，不枚举错误码表 |

**不写的内容**：时序要求、错误码枚举、接口URL、度量单位、精度容忍度（开发阶段在接口文档中定义）。

**长度控制**：每个子功能四段合计 ≤30 行。

### 4.4 操作步骤

**步骤 1 — 编写文字内容**

在 Claude Code 中按精简模板逐个子功能编写，全部写入 `详细规格说明.md`。

**步骤 2 — 生成流程图（按需）**

对涉及多步骤处理、条件分支、异常路径的子功能生成流程图。简单逻辑（如单步计算、纯配置操作）可跳过。

```
/drawio-skill 画一个流程图，描述子功能 X.Y（{子功能名称}）的处理流程。
要求：
- 主流程使用简洁的直线连接（不用正交拐弯线），形状中心对齐
- 分支流程使用正交路由
- 包括正常流程、异常分支、校验节点
- 文件保存到 docs/功能模块需求分析/模块X-名称/流程图/drawio/flow-X.Y-名称.drawio
```

## 五、完整执行流程（汇总）

### 5.1 准备工作

确保以下文件存在且是最新版本：
- `docs/lingolab-ai-v1.0-prd.md`

### 5.2 执行命令汇总

按顺序在 Claude Code 中执行：

```
# === 阶段 1：子功能拆解 ===
参考 PRD 中的模块 X，拆解为子功能，用 (1) (2) 编号格式，
写入 docs/功能模块需求分析/模块X-名称/子功能清单.md

# === 阶段 2：用例图 ===
/drawio-skill 画模块 X 的 UML 用例图，
保存到 docs/功能模块需求分析/模块X-名称/用例图/drawio/模块X-用例图.drawio

# === 阶段 3：逐个编写子功能详细说明 ===
# 对每个子功能：
#   a. 按工作流模板编写文字内容（需求/输入/处理/输出），写入 详细规格说明.md
#   b. 生成流程图，保存到模块文件夹内
```

### 5.3 执行顺序

```
模块选定 → 阶段1(拆解) → 【审核】 → 阶段2(用例图) → 【审核】
                                                        ↓
                                              阶段3(每个子功能)
                                              ├── (1) 文字 + 流程图
                                              ├── (2) 文字 + 流程图
                                              └── ...
                                                   ↓
                                              【最终审核】
```

## 六、流程图绘制规范

### 6.1 箭头线为什么弯弯扭扭？

draw.io 的 `edgeStyle=orthogonalEdgeStyle`（正交样式）会让连线以直角拐弯的方式路由。如果形状没有严格中心对齐，就会出现不必要的拐弯。

**正确做法：**

- **上下直连的形状**：不要用 edgeStyle 属性，使用默认直线连接。同时确保所有垂直直连的形状共享相同的水平中心坐标（centerX 一致）。
- **分支路径**（如错误处理）：使用 `edgeStyle=orthogonalEdgeStyle` 做直角拐弯是合理的。
- **主流程**：`style="html=1;exitX=0.5;exitY=1;entryX=0.5;entryY=0;"`（纯直线）
- **分支流程**：`style="edgeStyle=orthogonalEdgeStyle;rounded=1;orthogonalLoop=1;jettySize=auto;html=1;"`（正交路由）

### 6.2 布局规范

- 主流程中的形状保持相同 centerX，从上到下排列
- 分支流程从主流程的左侧或右侧水平引出
- 形状间距：垂直 80-100px，水平 ≥200px

## 七、团队协作指南

### 7.1 角色分工

| 角色 | 职责 |
|------|------|
| **产品经理** | 发起模块分析任务，审核子功能拆解是否完整，审核需求描述是否准确 |
| **开发人员** | 执行 AI 辅助编写，审核技术细节（输入/输出/处理/异常），确保可开发 |

### 7.2 任务分配方式

**按模块分配（推荐）：** 每人负责 1-2 个完整模块，端到端完成三个阶段。每个模块的产物放在独立文件夹中。

### 7.3 Git 分支命名

```
docs/module-{编号}-analysis    # 如 docs/module-1-analysis
```

## 九、常见问题

### Q1：一个模块拆多少个子功能合适？

一般 3-5 个。太少说明粒度太粗，太多说明拆得太碎。

### Q3：用例图和流程图的区别？

- **用例图**（阶段 2）：角色与功能的交互关系，用椭圆+火柴人
- **流程图**（阶段 3）：系统内部处理步骤，用矩形+菱形+箭头
